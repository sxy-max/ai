# Go AI 统一内容标准（Unified Content Standard）

> 交付物之一：两份用户权威标准的整合版本。
> 权威输入（完整保留原文语义，不做改写）：
> - `D:\codex\skills\写作\structure-standard.md`（HARD COMPOSITION CONTRACT）
> - `D:\codex\skills\写作\关系修辞表达生成器.md`（EXPRESSION SCHEDULER）
> 代码落地：`lib/content-standard/`（原文常量 + 复杂度决策 + 注入文本）；注入点见文末。

## 1. 两份文件是什么

| 文件 | 管辖 | 核心链条 | 硬性要求 |
|---|---|---|---|
| structure-standard.md | 结构 / 推理主线 / 取舍 / 密度 / 上下文一致性 / 完成测试 | phenomenon → relationship → mechanism → constraints → deduction → conclusion → transfer | 不机械打印标签；一个中心判断；一条主线；例子只在真正有用时加入；必要边界；及时结束；删掉不贡献的段落 |
| 关系修辞表达生成器.md | 表达调度（先判断关系，再选择修辞） | 现象 → 关系 → 机制 → 约束 → 推导 → 结论 → 迁移 | 对比划界 / 类比映射结构 / 比喻降抽象 / 设问推进；每个修辞必须回答「它让哪个关系变清楚了？」；答不上就删 |

## 2. 潜在冲突与最终解决（用户规则）

存在真实张力：

- A（structure-standard）：不机械输出内部标签；不必要不扩写；例子只在有用时加入；能结束就结束。
- B（关系修辞表达生成器）：完整解释/知识/议论型内容对四种高频修辞给出高权重，并提供默认结构模板。

**最终统一标准：HARD STRUCTURE FIRST + FUNCTIONAL RHETORIC SECOND。**

1. 先满足中心判断和因果/关系主线。
2. 再判断哪里真的存在：混淆 / 抽象 / 复杂机制 / 推进需要。
3. 只有在对应关系存在时调用相应修辞。
4. 修辞权重是选择优先级，不是机械句子配额。
5. 如果某修辞没有使关系更清楚，则根据原文件自己的规则删除。
6. 短答案不为了凑四种修辞强行扩写。
7. 完整解释型/知识型/议论型长内容，应主动检查是否有机会使用高优先级修辞帮助理解。
8. 可见输出默认不打印：现象/关系/机制/约束/推导/结论/迁移。
9. 如果用户明确要求结构化提纲/报告，可以使用自然、内容相关的小标题。
10. 不允许因为使用 Standard 而产生机械模板感。

## 3. 硬规则（解释、分析、比较、推荐、研究、知识型用户输出）

- 写之前内部确定：「用户读完以后最应该突然明白什么？」只能有一个主判断，然后建立一条关系主线。
- 两个概念容易混淆：不要先分别堆定义。直接让差异可见：不同输入/状态 → 不同机制 → 不同结果 → 不同选择。
- 讲机制：不要只说「X 很重要，因为有 A/B/C 优点」。表达 X 改变了哪个变量 → 这个变量让什么发生 → 后面的现象为什么出现。
- 例子：只有在能暴露隐藏关系时使用。优先结构：对象 → 动作 → 变量变化 → 结果变化 → 为什么。必要时做反事实。
- 边界：只补真正影响判断的条件。不要为了「完整」堆例外。
- 结尾：关系模型已经完整时及时停止。不要重新把全文总结三遍。

## 4. 修辞调度规则（保留用户文件的功能定位）

| 修辞 | 功能 | 触发条件 |
|---|---|---|
| 对比 | 划边界 | 存在容易混淆的概念 |
| 类比 | 映射结构 | 机制复杂、有熟悉结构可映射 |
| 比喻 | 降低抽象 | 概念太抽象 |
| 设问 | 推动阅读路径 | 需要推进时（不是卖关子） |
| 排比 | 铺层次 | 真正存在多个并列变量 |
| 反复 | 钉住中心判断 | 主判断需要被钉住 |
| 衬托/反衬 | 放大主体/落差 | 差异本身帮助理解时 |
| 对偶 | 收束关系 | 段尾收束记忆点 |
| 双关、借代 | — | 默认禁用（除非用户明确要文学用途） |

**RELATION → RHETORIC，不是 RHETORIC → CONTENT。** 不得先选修辞再往里面塞内容。

## 5. 按任务复杂度自适应（内部层级，不向用户显示名称）

- **SHORT / DIRECT**（如「HTTP 400 是什么意思？」）：直接说关键关系和结果。不强迫类比/比喻/长例子/七段结构。
- **NORMAL EXPLANATION**（如「PCB 打样是什么意思？」）：一个中心判断 + 概念关系 + 机制 + 必要例子 + 边界。
- **DEEP ANALYSIS / DOCUMENT**（技术架构比较、复杂决策、研究报告）：完整使用结构链 + 关系比较 + 机制 + 约束 + 推导 + 迁移 + 合适修辞辅助。

这是内容复杂度适配，不是三个新的 Agent。

## 6. 适用范围

**作用于**：用户可见解释、分析、比较、推荐、知识回答、Research summary、Markdown 文章、需要内容组织的 DOCX/PDF、PPT 内容规划中的语言组织、网页知识内容。

**不作用于**：代码源码、JSON、日志、Tool Result、命令输出、机器状态、错误栈（保持原生结构）。

## 7. 反模板护栏（回归禁止项）

- 每个答案固定七个标题 → 禁止
- 每个回答必出现「为什么会这样？」 → 禁止
- 短问题强行塞比喻 → 禁止
- 为完成修辞比例制造无意义类比 → 禁止
- 一个结论换三种说法重复 → 禁止
- 堆术语 → 禁止
- 「看起来很深」但无法指出变量关系 → 禁止
- 给每段添加无意义总结 → 禁止
- 过度扩写用户问题 → 禁止
- 结构标准变成固定模板 → 禁止

## 8. 注入架构（在 Claude Code 生成内容之前进入，不做事后第二模型润色）

```
Preflight / Context 选择
  ↓ 任务需要用户可见内容表达（解释/分析/文档类）
Content Standard（lib/content-standard）
  ↓
Claude Code 从一开始按标准生成
  ↓
Display 只渲染，不重新写作
```

| 通道 | 注入点 | 逻辑 |
|---|---|---|
| 任务系统（Claude Code 主链） | `lib/tasks/worker.ts` → `standardForTask(goal, type)` | 代码/机械任务不注入（`MECHANICAL_SIGNALS`）；其余按复杂度注入 short/normal/deep 三档 |
| Chat 生产链（CLAUDE_CHAT_ENABLED） | `app/api/chat/route.ts` `claudeCodeChat()` | `detectSkill` 命中 academic/analysis 时，`[写作标准]` 段置于用户要求之前（防截断） |
| Chat 开发直连链 | `app/api/chat/route.ts` `skillText` | `skillInstruction` → 学术/分析类附加 `contentStandardText(complexity)` |

两份原文完整保留于 `lib/content-standard/structureStandard.ts` 与 `rhetoricGenerator.ts`（测试断言原文关键句存在）。
